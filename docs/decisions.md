- 2026-11-07: KX* daily-high series settle on The Weather Company's reported maximum for a named NWS climate site (e.g. "New York City (CLINYC) ... according to The Weather Company"); legacy HIGH* series cite the NWS CLI report. Evidence: archived rules_primary 2026-10-07; live KXHIGHTATL rules 2026-11-07.
- 2026-11-07: Supersedes the matching rule in 2026-10-07. Discovery matches a daily series when its title has a temperature word, a high signal (high/highest/max/maximum in the title, or HIGH in the ticker), and no low word (low/lowest/min/minimum) or derived word (difference/change/anomaly). The old phrase regex required "<high word> temperature in" and missed 41 of 59 live series ("Atlanta Max Temperature", "Daily high temp Tokyo"), losing their order books since collection began. A test asserts the exact 59-ticker set from a real /series fixture, so any rule change shows up as a diff. Principle: over-collecting is cheap and filterable at parse time; a missed series is unrecoverable.
- 2026-11-07: /series is fetched unfiltered and inactive series stay polled. A category filter would silently drop HIGHNY0/KXHIGHNY0, which Kalshi files under World; inactive series cost ~35 cheap requests per cycle and may reopen.
- 2026-11-07: Order books come from GET /markets/orderbooks in chunks of 50 tickers, sent as repeated tickers= params, each response archived as one envelope with the exact ticker list in request_params. A chunk counts as failed on any error or when the returned ticker set differs from the request (unknown tickers return HTTP 200 with an empty book), and then falls back to per-market requests for that chunk only. Evidence: 59 series with single-book requests took 347 requests and 43-44 s cycles on a 60 s tick, projected ~73 s once international markets list; batching gives ~66 requests and 16-18 s on the VM. 50 not 100: batch items are billed per ticker (10 tokens each), and 100 would exceed the 600-token burst.
- 2026-11-07: /markets requests are spaced 0.25 s apart; all other requests 0.1 s. Back-to-back /markets calls hit an undocumented unauthenticated limit of roughly 4-5 req/s (1-4 429s per cycle); spacing gave 0 429s for about 2 s per cycle. Repeatedly exceeding an undocumented limit risks an IP block.
- 2026-11-07: NWS collector archives /points, forecast, forecastHourly and forecastGridData every 30 min for each Kalshi settlement site, using the same raw envelope as Kalshi. Sites live in a checked-in config/nws_stations.csv derived from archived rules_primary; each CLI-to-station mapping is verified against api.weather.gov/stations and the NWS CLI page, never inferred from the code's letters. /points is cached, refreshed every 24 h, and the last valid mapping is kept when a refresh fails. One request per second; NWS publishes no numeric limit. Redirects are archived and not followed. Started before the spike because past NWS point forecasts are not known to be archived anywhere else.
- 2026-11-07: Transport failures with no HTTP response (timeouts, resets) are logged, not archived as synthetic envelopes, in both collectors. Gaps in raw/ are explained by logs until the planned heartbeat exists.
- 2026-11-07: Collection always has priority over maintenance jobs. Compaction's first production run hit a month of backlog at zstd level 19, used ~100% CPU and 317 MB RSS, and pushed the Kalshi cycle from ~12 s to 95 s, skipping ticks. The timer was disabled until compaction has a per-run time budget, streaming memory, a measured compression level and a hard CPUQuota.
- 2026-11-10: Supersedes the compaction defaults in 2026-10-28 (zstd 19, unbounded runs, late files merged by rebuilding the archive). Compaction runs hourly with a 120 s time budget, oldest hours first, streaming with bounded memory (~50 MiB RSS), at zstd level 9 without long-distance matching, under CPUQuota=20%, CPUWeight=20, IOWeight=10 and nice 10. Published archives are never rewritten; late files go into supplementary `YYYY-MM-DDTHH.late-N.tar.zst` archives, so the planned bucket sync only ever uploads new files. Evidence (quota-limited VM, one real hour of 103 MB JSON): level 19 cost 31.6 CPU s for 80x, level 9 cost 4.6 CPU s for 50x, level 3 cost 4.0 CPU s for 26x. Levels 3 and 9 both fit three hour-pairs per run, so level 9 halves archive size at no capacity cost; level 3 with long-distance matching matched the ratio but used 130 MiB. Modeled capacity is about 3x incoming. Verified in production 2026-11-10: 3-4 backlog hours per run with Kalshi cycles unchanged at ~16 s.
- 2026-11-11: Backup adds an hourly upload of published compaction archives to a us-east1 Standard bucket (`kalshi-weather-bot-raw-prathikn20`), which the 2026-11-07 snapshot decision left out. Uploads are write-once: objects are created with if_generation_match=0, and the VM runs as a dedicated service account holding only objectCreator and objectViewer on that bucket. Every run calls the bucket's testIamPermissions for storage.objects.delete and refuses credentials holding it, aborting on check errors too: the SDK may attempt deletion after a resumable-upload CRC32C failure, so delete protection is checked at runtime instead of assumed from deployment. The permission check needs no extra IAM permission and is one Class B operation. A local ledger (`state/raw-sync.sqlite`) records each upload whose stored size and CRC32C match the local file, so the bucket is never listed (objects.list is Class A; the free tier is 5,000 Class A ops a month). The backlog is about 1,700 uploads and steady state about 1,500 a month. objectViewer exists so that a 412 after a crash or a retried upload can be checked: the object is accepted only if identical, otherwise the run fails loudly. No Bucket Lock: a locked policy is irreversible, and soft delete (default 7 days) already covers accidental deletion. Runs hourly at :40 with a 300 s budget under the same CPU limits as compaction. Sync holds compaction's raw/.compact.lock with a nonblocking exclusive flock for the entire run, warning and skipping if held; this shared lock prevents overlap during timer catch-up or overruns, while the :40/:10 offsets only spread routine work. Systemd TimeoutStartSec=15min bounds the oneshot run so a hung upload is terminated and releases the lock. The ledger's resolved path must be outside raw/. Limit: the bucket shares the project and account with the snapshots, so it is not off-site. Its value is a one-hour recovery point instead of 24 hours, a copy the VM can't delete, and a way to get data to the Mac without SSH. The default compute account's scopes are storage read-only, so this needs the service-account swap, which requires a VM stop.

- 2026-11-12: CI sets `UV_LOCKED=1` for the whole job, so `uv sync` fails when uv.lock is stale relative to pyproject.toml, and no `uv sync`, `uv run`, `uv lock` or `uv add` in the job can rewrite the lock. Before this change, plain `uv sync` silently re-locked and still passed, so CI could test versions the VM never installs. One job-level variable covers every step, including future ones. Per-step `--locked` flags only cover the steps that remember them. The deploy/*.service units keep plain `uv run`: a lock mismatch there would stop collection, and CI is what guarantees that the lock the VM pulls matches pyproject.toml. Limit: main has no branch protection, so a red CI run does not block a merge.

- 2026-11-13: Live forecasts and historical backfills use AWS NDFD `noaa-ndfd-pds/wmo/maxt/` so training and live inputs share one source; the `api.weather.gov` collector continues as a cross-check.
- 2026-11-13: Backfilled forecasts use `available_at = WMO filename time + L`, where L is measured from arrival logs as `first_seen_at - WMO filename time`, replacing the spike's eight-observation estimate. Observations are censored and excluded from L when the key's filename time precedes the previous successful poll (collector startup or outage).
